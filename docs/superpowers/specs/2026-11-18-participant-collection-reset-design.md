# Participant collection reset - approved design

Admin-only Manage collections is available from Participants and Analytics journeys. Show every event gate, effective collection count/allowance, remaining slots, prerequisite state, active collection timestamps and reset history. Undo one chosen/latest collection or explicitly reset all active collections at one gate. Require a reason and a review/confirmation step. No whole-event wipe and no automatic downstream cascade.

A read-only SHA-256 state token covers participant/gate identity, current activity status, gate rules, selected-gate effective collection IDs, revision and downstream collection impact. The reset transaction recomputes this token; stale confirmations return 409. Reset operation UUIDs and a canonical request hash make network retries safe and prevent the same reset being applied to a subsequent new collection. Keep original scans and soft-reverse selected collections, recording actor/time/reason and linking every reversed collection to a reset batch.

Each participant/gate has a monotonically increasing collection revision. Every device capture saves the revision known at capture time in the durable queued operation. A reset increments only that participant/gate revision. Missing revisions are treated as legacy revision zero. Existing historical undos are backfilled into revisions. Queued operations with an older revision are acknowledged as rejected conflicts and require a fresh physical scan; they are never rewritten and retried with a newer revision. Device heartbeat, Sync now and conflict responses refresh future captures. This uses revision checks, not unverified device clocks.

A replay of an original successful operation whose collection was reversed returns a current reversal annotation, without changing the historical scan/audit or adding a collection. Other original rejection replays predating a reset receive a reset-conflict annotation. Participant deactivation and QR signature/event checks remain authoritative. Normal idempotent replays without resets keep the original result.

Resetting a prerequisite preserves downstream deliveries; the UI warns about related completed gates if the reset removes the final effective prerequisite collection. Future scans continue enforcing direct prerequisites. Entrance-gate resets disclose attendance/arrival-time impact. Resets update effective counts, analytics and exports, while historical successful attempts remain in the audit.

The legacy single-collection undo API delegates to the same transactional/versioned service so it cannot bypass offline protection. The new UI replaces browser prompts and provides snapshot-bound confirmation, a reason, explicit impact acknowledgement and safe retry after a lost response. A shared collections component serves both entry points. Resets in analytics always concern current full-event state, independently of the analytical date filter; refresh the affected journey, participants and dashboard after completion.

Tests cover same-QR re-collection, one/all scope, multiple allowances, repeats, stale snapshots, dependencies, deactivation, cross-event isolation, authorization, reset retries after new collections, old/new offline captures, reversed operation replays, legacy undo, analytics/export reconciliation and browser flows.
